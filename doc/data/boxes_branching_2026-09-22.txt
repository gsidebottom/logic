# Branching experiments (2026-09-22), following the set-covering profile
# (boxes_profile_2026-09-22.txt): CaDiCaL reaches a conflict every 1.35
# decisions there, we need 3.1.  Is it the decision order?

# === 1. VMTF in place of VSIDS (BOXES_BRANCH=vmtf) ===
#
# Variable move-to-front as CaDiCaL and Kissat run it in focused mode: a
# queue by last-bump stamp, the decision taken from the newest unassigned
# entry (a search pointer walking toward older entries, reset on backjump
# to the newest variable unassigned), the variables of each conflict moved
# to the front in the order of their old stamps, eliminated variables
# dequeued; trail reuse on restart compares stamps.  Everything else
# (EMA restarts, phase saving, reduce policy) as in the default engine.
# Brute-force tested (random_vmtf_vs_bruteforce).
#
# A/B on the 18 fast balanced-set instances plus set-covering, same
# binary, both arms per instance in alternating order, 400 s cap,
# verdicts checked.  Conflicts B/A (VMTF over VSIDS):
#
#   first run, queue built highest index first:
#     median 1.94, fewer on 4/15; four instances VSIDS solves in 0-12
#     conflicts went to the cap (cryptography 12 -> 2.0 M, software-bmc
#     0 -> cap, ascon 65 K -> 5.6 M, set-covering 1.3 M -> 2.2 M);
#     graph-isomorphism 426x, argumentation 7.7x, multiplier 10 -> 78.
#     That is the INITIAL order, not the queue: VSIDS breaks ties at zero
#     activity lowest index first, and these instances' numbering is the
#     structure (inputs before outputs).
#
#   controlled run, queue built lowest index first (VSIDS's first decisions):
#     cryptography 12 -> 12, multiplier 10 -> 10, software-bmc 0 -> 0,
#     relational 72 -> 81: the blow-ups were the order.  What remains is
#     the dynamics --
#       wins   subgraph-isomorphism 0.23, petrinet 0.52, software-verif 0.70,
#              hashtable 0.94, ascon 1.00
#       losses ramseycube 33x, graph-isomorphism 8.6x, floodit 3.7x,
#              argumentation 2.7x, planning 2.5x, set-covering 1.9x (cap)
#     median 1.035, fewer on 5/17 (sign test p = 0.14); wall median 0.97
#     (the O(1) bump shows on the small instances), faster on 10/17.
#
#   On set-covering itself -- the profile's instance -- VMTF makes us
#   worse: 2.47 M conflicts at the 400 s cap against 1.31 M, and no
#   faster per conflict.  The queue alone is not CaDiCaL's 1.35
#   decisions per conflict; its advantage lives in the combination
#   (focused/stable alternation, reason-side bumping, target phases) or
#   elsewhere.  VMTF stays as an option, off.
#
#   Lesson for every branching A/B here: control the initial order first;
#   four of the fast set are decided by it alone.
