=== Conclusion ===
#
# Deletion AGGRESSION is not the lever.  Our default frac=2 is at or near a
# local optimum: frac=1 is clearly worse (a timeout on w55_178, 2-3x on the
# circuits) and frac=3/4 are neutral once the volatile instance is removed.
# And "delete more" does not transfer from CaDiCaL anyway, because the two
# knobs act on different pools: CaDiCaL's 75% applies to CANDIDATES, with
# tier1 never a candidate and recently-used tier2 clauses granted a grace
# period, while our frac applies to the whole database behind only
# glue<=2/binary/reason protection.
#
# What the CaDiCaL side points at is WHAT IT PROTECTS.  The one arm that
# consistently hurt was collapsing tier2 into tier1 (1.30x) -- removing the
# grace period for recently-used mid-glue clauses -- while freezing the
# dynamic tier recomputation entirely did NOT hurt (0.917x).  So if this
# lever gets built, build the `used`-counter grace period, not the dynamic
# percentile tiering and not a blunter deletion fraction.
#
# Confidence: low.  Ten instances cannot price an effect whose per-instance
# swings reach 28x.  This says what to build FIRST if we build it, not that
# it is worth building.
