# STEP2 CONES EXIT
#
# === Reading the cone half ===
#
# Inside CaDiCaL the same cones win where they never won in our engine and
# lose where they won.  Wins: toughsat_factoring 108.8 s -> 50.2 s (2.05 M
# -> 891 K conflicts, 2.0 M table propagations), ezfact64_6 21.0 -> 17.9 s
# (445 K -> 336 K).  Losses: pyhala-braun-sat 25.7 -> 145.3 s (455 K ->
# 1.49 M conflicts) -- the instance our engine's cones took from 143 s to
# 29 s -- pyhala-unsat 53 -> 121 s, the ISCAS pair 4x.  Timeouts unchanged.
# Two costs are structural to the interface: every observed variable is
# frozen, so CaDiCaL's elimination and inprocessing cannot touch the cone
# variables (853 cones on pyhala), and each table propagation is a callback
# with a lazily built reason of 5-9 literals against a watched clause.
# The factoring instances (multiplier cones, long UNSAT-ish searches) pay
# for the propagator; pyhala, which our engine solves through the tables'
# conflicts (77% of them), CaDiCaL solves better on the clauses alone.

# STEP2 NATIVE EXIT
#
# === Reading the native half ===
#
# Against our own engine on the same residual + boxes, CaDiCaL with the
# boxes wins 13 of 14, often by an order of magnitude and more: cn120 k=8
# 2.9 s -> 0.3 s, mm_boxes_sym(2;7) 4.3 s -> 0.03 s, w5_ap(177) 35 s ->
# 12 s, w5_ap(178) 130 s -> 46 s, sun56[1,2,4] from the cap to 21-34 s.
# The CDCL core is the difference, on box-native instances as on cones.
#
# Against CaDiCaL on the expanded CNF, the propagator wins only the small
# satisfiable rows, by tenths of a second (sun56[0,5,7] k=8 0.08 vs 0.23,
# cn120 k=8 0.32 vs 0.44, mm(2;7) 0.03 vs 0.10, i12/i19), and loses the
# harder ones by 2-40x: sun56[1,2,4] k=14 33.5 s against 0.83 s, w5_ap(177)
# 12 s against 0.6 s, w5_ap(178) 46 s against 18 s, mm(2;6) 0.66 against
# 0.22.  These tables are small -- 4-13 rows per box on average -- and a
# four-row table over five variables is four clauses' worth of structure:
# CaDiCaL's watched propagation over the expanded CNF, with elimination
# and inprocessing free to act on every variable, beats a callback-driven
# table oracle whose variables are frozen.
#
# A caution on the record: the box-native rows in doc/box_backend_design.md
# ("boxes 2-25x faster than CaDiCaL on the satisfiable windows") came from
# the web app's hybrid -- matrix-method path enumeration over the residual
# with the engine completing prefixes against the tables -- not from a CDCL
# search over residual + boxes, which is what the CLI runs here and what
# loses to CaDiCaL plain on the same rows.  The two are different searches.
#
# === Answer ===
#
# Adding the box technology to CaDiCaL is a win over our own engine
# everywhere it was tried, and a win over plain CaDiCaL exactly where the
# tables absorb structure that clause propagation loses: the multiplier
# cones of the factoring instances (toughsat 108.8 -> 50.2 s, ezfact64_6
# 21.0 -> 17.9 s) -- the adder of s1 of the design doc, at last measured
# end to end -- and nowhere else.  Small tables are clauses; the interface
# costs (frozen variables, a callback per propagation, reasons of 5-9
# literals built at analysis) are paid on every row.  If the box idea has a
# future in a CDCL core, it is as a propagator for arithmetic cones with
# wide tables, chosen per box by the propagation it adds over the clauses
# it replaces -- not as a general encoding.
