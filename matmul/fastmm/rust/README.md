# fmm: fast matrix multiplication on Apple silicon, in Rust

The Rust port of the C library in `matmul/fastmm` (`fmm.h`): C = A B for row-major f32 or f64
matrices, n x n or an m x k matrix A times a k x n matrix B, by fused levels of the rank-48
<4x4x4:48> scheme of Dumas, Pernet and Sedoglavic (their 262-operation accurate program,
PLinOpt's 4x4x4_48_accurate_262), of their accurate <3x3x6:40> scheme in its three orientations
(rectangular levels: a plan tracks the shape of every level's products) and of a <2x2x2:7> level
(DPS's dyadic accurate point of ISSAC 2024; Strassen-Winograd's programs with `gen_kernels.py --sw
winograd`) over Accelerate's GEMM, with GEMM streams, pipelined passes and padding, as a
calibrated planner picks for this machine, shape and precision.  On an M4 Pro, from n = 3000 to
16384, it is 1.04-1.60x (f32) and 1.29-1.99x (f64) faster than Accelerate's GEMM, with the C
library's plans, speed and results (bit for bit).

```rust
let mut c = vec![0.0f64; n * n];
fmm::dgemm(n, &a, n, &b, n, &mut c, n, 0.0)?;   // max_growth 0: the default budget (no less accurate than the GEMM); -1.0: the fastest plan
fmm::sgemm(n, &x, n, &y, n, &mut z, n, 4.0)?;   // error growth at most 4x the classical GEMM's
fmm::sgemm_mkn(m, k, n, &x, k, &y, n, &mut z, n, 0.0)?;   // an m x k matrix times a k x n matrix
```

Once per machine, calibrate (about 8 minutes, the machine otherwise idle):

    cargo run --release --bin fmmcal          # sizes up to 16384, both precisions

The cache (`~/Library/Caches/fmm/calib5_f32.txt`, `calib5_f64.txt`, or `FMM_CALIB_DIR`) has the
C library's format; either library reads the other's.  Square sizes between the calibrated ones
are interpolated; a rectangular shape is priced from the square measurements (GEMMs by their
flops, passes by their traffic: an estimate) until `fmm::calibrate_mkn(m, k, n, f64)` measures
it.  Without a calibration covering a shape every call runs Accelerate's GEMM, so results are
always correct.  `fmm::plan(n, f64, max_growth)` and `fmm::plan_mkn(m, k, n, f64, max_growth)`
tell which plan a call runs and its predicted time and error.  `max_growth` is the error budget on the plan's
predicted error over the GEMM's: 0 the default of 1 (a plan predicted no less accurate than the
GEMM it replaces; the plans with a 2x2 level on top qualify too since the level's programs are
DPS's dyadic point, where Strassen-Winograd's needed a budget of 2), a positive value that budget,
a negative value no budget (the fastest plan).  The model: the GEMM's
own error against the exact product, one factor per level measured one level over the GEMM at
2304, and a depth factor once per level after the first, all from the calibration.

## With the GPU (f32)

    cargo build --release --features gpu

compiles the C library's `gpu_leaf.m` (Metal Performance Shaders' matrix multiplication on shared,
uncopied memory) into the crate and plans as the C library's GPU build (`libfmm_gpu.a`): a
level's products shared between the GEMM streams and the GPU (leaves `GM`, `G6M`), pipelines over
`G6M`, and on top the classical product in strips of rows (`K16`, `K32`, `K64`), with the same
rules (products of 576 and up, an 8% tie window, GPU plans held to the predicted error of the
fastest plan without the GPU).  The GPU's product is Accelerate's bit for bit, so results do not
depend on which engine took which product.  Its calibration entries live in
`calib5gpu_f32.txt` beside the cache, shared with the C library; `fmmcal` measures them too.
The workspace starts on a page and is wrapped for the GPU while it lives; a K level wraps the
caller's matrices for the call, which takes matrices starting on a page whose whole pages cover
them (large `Vec`s do), else the best plan without a K level runs.  `FMM_GPU=0` plans without the
GPU; f64 is unchanged.

Unsafe code: only `src/sys.rs`, the FFI declarations of Accelerate's two GEMMs and its threading
switch and of the threads' scheduling class, behind safe wrappers that check the slices, and two
`asm!` instructions on aarch64: `mrs dczid_el0` (the size of the block `DC ZVA` zeroes) and
`dc zva`, which the passes use to claim the cache lines they are about to overwrite, so that the
stores do not first read them from memory.  Its safe wrapper `claim_lines` takes a `&mut` slice
and zeroes only aligned blocks wholly inside it (tested); `FMM_ZVA=0` switches it off, and on
other architectures it does nothing.  With `gpu`, also `src/gpu.rs`: the FFI declarations of
`gpu_leaf.m`'s attach, detach, availability and batched sgemm, behind wrappers that wrap only
memory the crate holds (a `Pinned` buffer from creation to drop, or a caller's matrices inside
`with_attached` for one call) and check every product's slices against its extent.  The
kernels (`src/kernels.rs`) are safe Rust generated by `gen_kernels.py --rust` from the same
programs as the C kernels; the rest of the crate is `#![deny(unsafe_code)]`.

Tests and benchmarks:

    cargo test --release
    FMM_CALIB_DIR=... cargo run --release --bin fmmbench [n ...]    # against Accelerate (test_fmm's cases, rectangular ones included)

With `--features cbench` (links the C library: run `make build/libfmm.a` in `matmul/fastmm`
first): `passbench` (the D48 left-factor pass against the C kernel and driver) and `crosscheck`
(the Rust and C libraries on the same inputs and cache: plans and results, bit for bit); with
`--features cbench,gpu` against the C library's GPU build (`make build/libfmm_gpu.a`).  Run
the crosscheck with an absolute `FMM_CALIB_DIR`: it runs in `rust/`, and with a relative one
neither library finds the cache and only the classical GEMM is compared (`run_crosscheck.sh`).
